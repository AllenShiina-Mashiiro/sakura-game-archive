# V2.6-dev 本地 PostgreSQL 迁移计划

> 基准分支：`v2.6-dev`（从 `v2.5-dev` 创建）
> 目标运行方式：Next.js + Docker Compose + PostgreSQL 18.6
> ORM：Drizzle ORM
> 原则：保留现有页面与业务行为，优先替换数据访问层，不做无关重构。

## 已审查的现状

- `lib/db.ts` 将 users、games、resources、guides、feedback、notices、collections、loginLogs、comments、photos、siteSettings、shopProducts、inventory、coinTransactions、messages、friendships、notifications、contributors 全部装入单条 Supabase `app_state` JSON 快照。
- 读写通过 `getSupabaseAdmin()`、`app_state` 的 version 乐观锁，以及 Beta 2.0 RPC（`archive_load_snapshot` / `archive_save_snapshot`）完成。
- `lib/auth.ts` 使用 scrypt 密码哈希与自定义 HttpOnly Cookie Session；用户主键目前是 UUID，用户名字段为 username。
- `app/api/auth/register` 当前仅接受 username/password/nickname，不要求邮箱验证；`app/api/auth/login` 使用 username/password。
- 登录失败限流 `lib/login-rate-limit.ts` 依赖 Upstash Redis。
- `compose.yaml` 当前只编排 Next.js 网站，仍要求 Supabase URL 与 service role key；没有 PostgreSQL 服务。
- `ThemeEffects.tsx` 当前使用 CSS/字符花瓣，不是用户准备提供的博客粒子组件。
- `lib/types.ts` 列出了现有核心业务实体与字段；迁移需逐一核对所有 API 的读写方式，不能只按此文件推断完整约束。

## 目标架构

- PostgreSQL 是网站业务数据的唯一主数据库；Drizzle 管理 schema 与迁移。
- 内部用户主键继续使用 UUID，公开标识使用唯一的 `@username`。注册输入不含 @；规范为小写字母、数字、下划线，唯一索引保证不重复。
- 用户邮箱唯一并验证后才激活本地密码登录；验证码只存哈希，设置有效期、尝试次数、发送频率与用途，成功后一次性消费。
- Google/GitHub OAuth 使用独立 provider account 关联内部 UUID，不把第三方用户名当作内部主键。
- 会话、登录限流、验证码、OAuth state 均在本地服务端管理；登录限流不再强依赖 Upstash。
- 邮件发送通过可配置 SMTP/邮件服务适配器，密钥只在服务端环境变量。
- 网站与 PostgreSQL 由 Compose 编排，数据库仅暴露给 Compose 网络；本机开发如需 GUI/psql 管理，可保留 loopback 绑定。
- 图片/附件存储需独立审查。移除 Supabase 数据库不等于自动迁移 Supabase Storage；本地开发与 Ubuntu 部署需明确持久化目录/备份策略。

## 迁移阶段与验收门槛

1. **完整盘点（当前阶段）**：枚举所有 API、Server Actions、页面与组件中的数据库、认证、Storage、Redis 调用；形成实体字段/关系清单。
2. **数据库基础**：加入 Drizzle、PostgreSQL schema、迁移配置、健康检查与 Compose；启动后执行迁移并验证连接。
3. **数据访问层**：逐域替换 JSON 快照读写为事务化 SQL repository；保留 API 返回形状，逐组测试。
4. **认证**：邮箱验证码注册/登录、Google/GitHub OAuth、公开 @username；补充 CSRF/state、限流、邮件重放保护与会话撤销。
5. **存储与外部服务**：替换 Supabase Storage 和 Upstash 依赖，确定本地文件目录、上传限制、备份与恢复。
6. **视觉组件**：收到博客粒子组件后再替换樱花效果，避免凭印象仿制。
7. **验证与迁移**：lint、typecheck、build、API/权限测试、空库初始化测试；再制作 Ubuntu Compose 部署与备份恢复流程。

## 明确不做

- 不修改或清空 Supabase 云端项目。
- 不迁入旧用户、游戏或其他业务数据（本次目标为空库起步），但旧云端资源在本地版本验收前不做破坏性删除。
- 不将内部 UUID 批量替换成 @username 主键；前端展示与路由使用公开用户名，数据库关系保持稳定。
- 不在未盘点完所有读写点前移除旧 Supabase/Redis 依赖。
- 不重写无关页面、样式或功能。

## 当前阻塞/待确认输入

- 用户提到博客粒子组件将再次上传；在收到文件前不替换视觉效果。
- Google/GitHub OAuth 需要用户分别创建 OAuth App 并提供 Client ID/Secret（只通过本地环境变量配置，禁止在聊天中发送密钥）。
- 邮箱验证码需要 SMTP 或邮件服务账号与发件域名配置。
